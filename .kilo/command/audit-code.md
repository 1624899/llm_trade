# 代码审计提示词模板

> 将以下内容作为完整 prompt 发给 AI，替换 `{项目描述}`、`{项目名}`、`{审计范围}` 为实际内容。

---

## Prompt

你是一个高级代码审计工程师。请对 `{项目描述}` 进行全面审计，覆盖下列审计维度，并将所有发现整理到 `优化路线2.md`。

### 基本原则

- 结论必须基于代码证据，不要凭印象判断。
- 每个确定问题必须包含：文件路径、具体行号、相关代码摘要、影响、修复建议。
- 无法确认的问题不要写成确定缺陷，统一放入“待确认问题”。
- 功能升级建议只能作为长期改进，不得替代缺陷修复，也不得进入 P0/P1。
- 读取文件时必须使用 `Get-Content xxx -Encoding UTF8`，不要使用不带编码参数的 `Get-Content xxx`。
- 写入 `优化路线2.md` 时，按维度分批追加；每完成一个维度后立即写入，不要等全部审计完成再统一输出。

### 审计准备

1. 先读 `README.md`，理解系统架构、核心流程、CLI 用法、配置说明、数据库说明。
2. 再读 `config/config.yaml`，理解配置结构、默认值、阈值、开关项。
3. 按目录批量读取 `{审计范围}` 内的源码文件，优先并行读取，不要一个文件一个文件低效读取。
4. 审计范围默认包括：`src/` 全部模块、`main.py`、`config/`、`README.md`。如 `{审计范围}` 另有指定，以指定范围为准。

### 审计维度

#### 1. README 文档 vs 代码实现一致性

- 逐条对照 README 中描述的系统流程/工作流，在代码中找到对应实现。
- 检查步骤是否齐全，执行顺序是否一致，参数、阈值、默认值是否匹配。
- 检查 CLI 参数是否全部在 README 中有文档说明。
- 检查 README 中提到的功能是否都已实现。
- 检查代码中已实现但 README 未提及的重要功能，并记录文档缺口。

#### 2. 数据库表结构一致性

- 列出 README 中声称的所有数据库表，与代码中的 `CREATE TABLE` / schema 定义逐一比对。
- 检查 README 有但代码无的表、代码有但 README 未列出的表。
- 检查 `CREATE TABLE` 定义是否与 `ALTER TABLE` 迁移同步，即初始建表是否包含迁移新增列。
- 检查代码中实际读写的列是否都在 schema 中定义。
- 检查索引、唯一约束、主键、非空约束是否与代码查询和写入逻辑匹配。

#### 3. 逻辑缺陷

重点关注：

- **除零错误**：所有除法运算，检查分母是否有 `> 0` 或等价校验。
- **空值/None 处理**：`float(None)`、`int(None)`、数据库 NULL 读取后直接运算。
- **`or` 运算符误用**：`value or default` 会把 `0.0`、`""`、`False` 当作 falsy 穿透，应使用 `value if value is not None else default` 或更精确判断。
- **子串误匹配**：`"关键词" in text` 是否会在否定句中误报，如“未见 XX 风险”。
- **贪婪正则**：`r"\{.*\}"` 配合 `re.S` 是否会跨越多个 JSON 块匹配。
- **边界条件**：数组越界、空列表取 `[0]`、NaN 传播、日期为空、价格为 0。
- **默认值安全性**：数据获取失败时的默认动作是否符合交易安全原则，尤其关注默认买入、默认卖出、默认持有的风险差异。
- **异常吞噬**：`except Exception` 后是否静默返回危险默认值。

#### 4. 可靠性问题

- 检查外部 API、网络请求、行情源、LLM 调用是否有超时、重试、降级和错误日志。
- 检查数据库连接、文件句柄、缓存资源是否正确关闭或复用。
- 检查并发、批量任务、定时任务是否存在状态竞争或重复执行风险。
- 检查日志是否足够定位生产问题，是否存在占位符日志或过度静默。
- 检查配置缺失、环境变量缺失、数据文件缺失时是否有清晰错误信息。

#### 5. 冗余代码与重复定义

- 搜索项目中同名函数的多个定义，例如 `_to_float`、`_safe_float`、`_normalize_trade_date`。
- 搜索功能相同但实现不同的函数，例如不同文件中的价格获取、日期标准化、数值转换、JSON 解析回退链。
- 对每组重复定义给出行为差异表，至少包含：空值处理、异常处理、默认值、返回类型、调用方。
- 不要只写“有重复”，必须说明重复造成的具体维护风险或行为不一致风险。

#### 6. 死代码

- 搜索所有函数/方法定义，用 `rg` 或等价工具验证函数名是否在项目中被调用。
- 将死代码结论分为：高置信度、中置信度、低置信度。
- 对可能通过 CLI、反射、装饰器、注册表、字符串名称、测试入口调用的函数，不能直接判定为高置信度死代码。
- 检查 `if __name__ == "__main__"` 块中的临时测试代码。
- 检查注释掉的代码块，连续超过 2 行需记录。
- 检查占位符日志，如 `logger.info("log message")`。
- 检查 TODO/FIXME/HACK 注释，并判断是否影响正确性。

#### 7. 技术债

- **文件级**：列出超过 500 行的文件，并建议拆分方式。
- **接口级**：检查关键参数如 `codes`、`trade_date`、`db_path` 的类型标注是否一致。
- **资源级**：检查数据库连接是否复用，文件路径是相对路径、绝对路径还是配置路径。
- **魔数**：检查散落数字常量，如 `86400`、`0.35`、`9999`，是否应提取为命名常量或配置项。
- **测试缺口**：记录关键流程、边界条件、数据异常路径是否缺少测试。

### 执行要求

1. 必须先读 `README.md`，再读 `config/config.yaml`，然后读取源码。
2. 读取文件必须使用 `Get-Content xxx -Encoding UTF8`。
3. 源码检索优先使用 `rg`；如不可用，再使用 PowerShell 等价命令。
4. 每完成一个审计维度，立即追加写入 `优化路线2.md`。
5. 对于逻辑缺陷，必须给出具体行号，不要泛泛而谈。
6. 对于冗余代码，必须列出行为差异表，不要只说“有重复”。
7. 对于死代码，必须标注置信度，避免把动态调用误判为确定死代码。
8. 修复优先级定义：
   - P0：会崩溃、造成数据错误或产生高风险交易行为。
   - P1：影响正确性但通常不崩溃。
   - P2：影响体验、可观测性或维护效率。
   - P3：长期改进或功能增强。
