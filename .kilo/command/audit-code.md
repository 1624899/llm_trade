# 代码审计提示词模板

> 将以下内容作为完整 prompt 发给 AI，替换 `{项目描述}` 和 `{目标文件}` 为实际内容。

---

## Prompt

你是一个高级代码审计工程师。请对 `{项目描述}` 进行全面审计，覆盖以下 **6 个维度**，每个维度逐一检查，每发现一个问题立即记录到 `优化路线2.md` 中。

### 审计维度

#### 1. README 文档 vs 代码实现一致性
- 逐条对照 README 中描述的**系统流程/工作流**，在代码中找到对应实现
- 检查：步骤是否齐全？执行顺序是否一致？描述的参数/阈值/默认值是否匹配？
- 检查 CLI 参数是否全部在 README 中有文档说明
- 检查 README 中提到的功能是否都已实现，反之代码中有但 README 未提及的功能也要记录

#### 2. 数据库表结构一致性
- 列出 README 中声称的所有数据库表，与代码中 `CREATE TABLE` / schema 定义逐一比对
- 检查：README 有但代码无的表？代码有但 README 未列出的表？
- 检查 `CREATE TABLE` 定义是否与 `ALTER TABLE` 迁移同步（即 CREATE 是否包含了所有迁移添加的列）
- 检查代码中实际使用的列是否都在 schema 中定义

#### 3. 逻辑缺陷
重点关注：
- **除零错误**：所有除法运算，检查分母是否有 > 0 校验
- **空值/None 处理**：`float(None)`、`int(None)`、数据库 NULL 读取后直接运算
- **`or` 运算符误用**：`value or default` 会把 `0.0`、`""` 当 falsy 穿透，应用 `value if value is not None else default`
- **子串误匹配**：`"关键词" in text` 会在否定句（如"未见XX风险"）中误报
- **贪婪正则**：`r"\{.*\}"` 配合 `re.S` 会跨越多个 JSON 块匹配
- **边界条件**：数组越界、空列表取 `[0]`、NaN 传播
- **默认值安全性**：数据获取失败时的默认动作是否安全（如交易系统中默认"不卖"比默认"卖出"更危险）

#### 4. 冗余代码与重复定义
- 搜索项目中**同名函数的多个定义**（如 `_to_float`、`_safe_float`、`_normalize_trade_date`），对比每个定义的行为差异
- 搜索**功能相同但实现不同**的函数（如 `_get_latest_prices_batch` 在不同文件中的回退链差异）
- 记录每个重复定义的文件、行号、行为差异表

#### 5. 死代码
- 搜索所有函数/方法定义，用 grep 验证每个函数名是否在项目中被调用过
- 检查 `if __name__ == "__main__"` 块中的测试代码
- 检查注释掉的代码块（>2 行）
- 检查占位符日志（如 `logger.info("log message")`）
- 检查 TODO/FIXME/HACK 注释

#### 6. 技术债
- **文件级**：列出超过 500 行的文件及建议拆分方式
- **接口级**：关键参数（如 `codes`）的类型标注是否一致；数据库连接是否复用；文件路径是相对还是绝对
- **魔数**：散落在代码中的数字常量（如 `86400`、`0.35`、`9999`）是否有命名常量

### 执行要求

1. **先读 README.md**，理解系统架构和完整流程描述
2. **再读 config/config.yaml**，理解配置结构
3. **按目录批量读取所有源码文件**（并行读取，不要一个一个读）
4. **每完成一个维度的审查，立即追加写入** `优化路线2.md`，不要等全部完成再写
5. 对于逻辑缺陷，**必须给出具体行号**，不要泛泛而谈
6. 对于冗余代码，**必须列出行为差异表**，不要只说"有重复"
7. 修复优先级中，P0 = 会崩溃/数据错误，P1 = 会影响正确性但不崩溃，P2 = 体验/维护问题，P3 = 长期改进
